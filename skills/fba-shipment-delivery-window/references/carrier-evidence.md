# 尾程证据与改期建议

适用于美国 FBA 的“查询后建议”模式。用户已指定目标日期时走主技能的执行模式，不强制补查物流。

## 信息来源和衔接

```text
完整 FBA → 威飒等物流商取得尾程承运人及转单号
         → UPS/FedEx 等官方追踪：实际状态、预计日期、实际送达日期
         → 对照 Amazon 当前计划时段 → 建议 → dry-run → 批准 → 修改并回读
```

| 来源 | 用途 |
| --- | --- |
| 威飒、飞沃、云驼、天泰、九方或人工转单证据 | 核对 FBA、运单、目的仓及全部尾程单号的对应关系 |
| UPS/FedEx 等实际尾程承运商的官方追踪 | 提供是否收件、在途、预计送达和实际送达的证据 |
| Amazon | 提供当前计划时段、接收状态、编辑截止和日历可选范围 |

表格已有可靠的尾程单号与承运人时可直接查询尾程，不重复访问货代。物流商查询结果的 `eta=null` 或 ETA 缺项不阻断已经具备单号的尾程查询；货代的下单、到港、清关日期及转述轨迹均不能作为尾程官方结果。Amazon 时段只是计划，超过该时段不表示已实际送达。

现有物流商命令不查询 UPS/FedEx，也不自动生成目标日期。尚无独立尾程查询命令时，按 `ziniao-browser` 技能使用现有官方配对 Selenium 页面能力只读核验；无法取得官方结果则报告待核验，不伪装为已经具备自动查询能力。保留完整单号、匹配证据、追踪原文、官方来源、查询时间、日期类型和已知时区。

## 建议规则

| 已核实的尾程结果 | 建议 |
| --- | --- |
| 有有效预计日期，落在当前 Amazon 时段内 | 暂不调整 |
| 有有效预计日期，落在当前时段之外 | 建议该预计日期所在的日历周，仍需核对 Amazon 是否允许编辑 |
| 明确尚未送达，暂无预计日期，当前时段已过 | 标记需要顺延；建议至少查询日的下一日历周，标注“业务顺延，尾程预计日期未知” |
| 明确为“标签已创建、尚未收件”，暂无预计日期，当前时段为本周 | 按业务口径建议至少顺延到下一日历周，同样标注为业务顺延 |
| 已实际送达 | 不再按运输延误顺延；Amazon 接收状态独立读取 |
| 追踪页打不开、无结果、单号不符或状态无法判断 | 待核验；不能解释成尚未收件或据此顺延 |

“暂无预计日期”不等于“尚未收件”。只有承运商明确显示“标签已创建，收到包裹后提供预计时间”等证据，才归入未收件分支。UPS 已送达也不等于 Amazon 已接收；两个来源分别记录，冲突时暂停对应项。

日历周按周日到周六理解，执行使用 CLI 返回的 `target_window`。按目的仓当地日期判断是否跨周和超期；未知时区影响判断时先核实，不按执行机器的日期补猜。已经过去的预计日期不能直接用作新的目标日，报告信息陈旧并核验当前状态。

例：预计 2026-10-17 送达，对应 10/11–10/17。若核验日为目的仓当地 2026-10-20，UPS 明确未收件且没有预计日期，Amazon 当前为 10/18–10/24，则业务顺延候选至少是 10/25–10/31。这不是 UPS 给出的预计日期，也不表示 Amazon 一定允许修改。以上为规则示例，不是本次实票或实时查询结果。

## 从建议进入修改

- 逐票保留全部包裹对应；跨周、部分已送达、部分未知、号码覆盖不全或目的仓冲突时分别报告，不能取首个包裹代表整票。
- 分开报告“业务上需要调整”和“Amazon 是否允许执行”。当前仍要求 Amazon `orderStatus="已发货"`；已进入接收、编辑截止已过或日历不可选时，只报告需要调整但无法执行，不绕过门槛。
- 建议至少展示当前时段、尾程状态、预计/实际日期、来源及查询时间、建议周和原因。无预计日期的顺延单独标注，不把它填成承运商 ETA。
- 取得单号、读取追踪或生成建议均不代表批准修改；继续遵守主技能的 discovery、同参数 dry-run、明确批准、单次 apply 和页面回读。
